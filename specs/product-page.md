# Spec for Страница «О продукте» (product.html)

figma_component (if used): —

## Summary

Новая отдельная HTML-страница `product.html` — сжатый обзор продукта Amigo,
собранный по **двум источникам контента**: презентация
`amigo_presentation.pptx` (14 слайдов) + пять готовых визуалов-схем, и
**Google-документ Product Overview**
(`https://docs.google.com/document/d/1AuKQ5Npw6f7suTQSssODaQR1ryKTZyJH3t3CmCz-FjM`).
При расхождениях между источниками — уточнять у заказчика (см. Open Questions).
Самостоятельная страница в стиле сайта (по образцу
`privacy.html`), со своим URL, общей шапкой/подвалом и единой системой стилей
`css/style.css`. Пункт «О нас» в верхнем меню и в футере перенаправляется с
in-page-якоря `#about` на эту страницу.

Цель страницы: дать потенциальному клиенту цельное, но не перегруженное
понимание, что такое Amigo, какую проблему решает и как устроен
сбор/обновление данных — и подвести к заявке (демо-доступ) через
уже существующую lead-форму.

**Объём — расширенный вариант** (по решению заказчика). Поскольку на странице
добавляется внутристраничная навигация по разделам (см. FR-1b), описание
продукта делается более подробным: каждый раздел раскрывается содержательно,
а не одним абзацем. Перегруз всё равно не нужен — текст по делу, структура
читаемая, ориентир — материалы презентации + Google-док.

## Functional Requirements

### FR-1. Новый файл `product.html`
- Создаётся `product.html` в корне репозитория (рядом с `index.html`,
  `privacy.html`).
- Структура повторяет каркас `privacy.html`: тот же `<head>` (шрифты, Iconify,
  favicon), та же шапка с логотипом и навигацией, тот же `<footer>`, ссылка на
  общий `./css/style.css?v=N`.
- Язык — русский, разметка семантическая, доступная (заголовки по иерархии,
  `alt` у изображений, `aria-label` у интерактивных элементов).
- Никакого нового фреймворка/билд-шага. Только HTML + общий CSS (+ при
  необходимости общий `js/main.js`).

### FR-1a. Визуальное соответствие стилю сайта (обязательно)
- Новая страница должна выглядеть как органичная часть существующего сайта,
  а не как отдельный документ: те же шрифты, цвета, типографика, отступы,
  скругления, тени, кнопки и стиль секций, что и на `index.html`.
- Источник истины по стилю — общий `css/style.css` и его `:root`-переменные;
  переисповать существующие классы (секции, кнопки `.p-btn`, заголовки,
  контейнеры) вместо создания параллельных. Новые стили — только когда нет
  подходящего существующего, и в той же стилистике.
- Шапка и подвал — 1:1 с сайтом (как в `privacy.html`).
- Схемы-изображения вписываются в палитру/фон сайта (отсюда предпочтение
  PNG с прозрачным фоном для схемы архитектуры).
- Адаптив и поведение (бургер ≤768px, hover-состояния) — как на основном
  сайте; правило reduced-motion Variant B соблюдается (см. FR-6).

### FR-1b. Внутристраничная навигация по разделам (новое требование)
- На странице добавляется навигация по её разделам — ряд текстовых
  ссылок-якорей, как в примере `screenshots/00_32_sreen.jpg`: простые
  текстовые пункты, активный раздел подчёркнут, при нехватке ширины
  пункты переносятся на следующую строку (несколько рядов).
- **Расположение:** в `<body>`, **ниже шапки (header)**, отдельной полосой
  над контентом — это НЕ пункты основного меню в `<header>`, а отдельный
  внутренний навигатор по секциям `product.html`.
- Каждый пункт — якорная ссылка (`href="#section-id"`) на соответствующую
  секцию страницы; по клику — плавный скролл к секции (поведение
  согласовано с reduced-motion Variant B — скролл/анимации не отключаются).
- **Активное состояние (решение):** текущий раздел подчёркнут, как в
  примере, с **scroll-spy** — активный пункт автоматически переключается
  при скролле страницы (а не только по клику).
- Стиль строго по FR-1a: шрифт, цвет, типографика — из общего CSS/переменных;
  это не кнопки `.p-btn`, а текстовые ссылки в стилистике сайта.
- Адаптив: на узких экранах пункты переносятся (как в примере); поведение
  при бургер-меню шапки не конфликтует с этим навигатором.
- **Sticky НЕ делаем (решение заказчика):** навигатор — статичная полоса
  под шапкой (как в примере `00_32_sreen.jpg`), при скролле не прилипает.

### FR-2. Контент страницы (расширенный; презентация + Google-док)
Секции сверху вниз. Каждая секция (кроме Hero) имеет стабильный `id` —
он же цель пункта навигатора FR-1b. **Точный список разделов навигатора —
см. FR-2a.**

0. **Hero / заголовок** (без `id`, не пункт навигатора)
   - H1: **«Как работает Amigo»** (решение заказчика).
   - Подзаголовок: «Платформа автоматизации отчётности и рекламной аналитики».
   - Абзац-лид (2–3 предложения) из сути слайдов 1–4 + цели из Google-дока.

1. **Проблема** — `id="problem"`
   - Развёрнутый разбор тезисов слайда 2 (каждый — пункт с пояснением в
     1 предложение): данные в разных рекламных кабинетах; сбор и сверка
     статистики занимают время; ручная подготовка отчётов повышает риск
     ошибок; рекламные платформы пересчитывают данные задним числом;
     руководителям, сотрудникам и клиентам нужно единое окно аналитики.

2. **Что такое Amigo** — `id="what"`
   - Что делает Amigo: автоматизирует ключевые процессы рекламной
     отчётности — сбор статистики → проверка актуальности данных →
     обработка и нормализация → единая витрина (дашборды, Excel-отчёты,
     базы данных) → масштабирование под новые проекты.
   - Цель (Google-док): сократить время сотрудников на сбор статистики из
     множества рекламных кабинетов и исключить ошибки при подготовке
     отчётов; принцип единого окна; архитектура на микросервисах.

3. **Поток данных / архитектура** — `id="data-flow"`
   - Детализация (Google-док): **Data Lake (ClickHouse)** —
     сырые рекламные данные → **слой обработки** — обогащение/парсинг,
     добавление комиссий, НДС, кастомных группировок →
     **Data Mart (MySQL)** — обработанные данные → **визуализация** —
     дашборды Power BI и выгрузки в Excel.
   - Визуал: схема архитектуры. **Решение: `scheme_transparent_bg.png`**
     (прозрачный фон — FR-1a), прогнать через оптимизацию.

4. **Источники данных** — `id="sources"`
   - **Финальный список (решение заказчика):** Яндекс Директ, VK Ads,
     MyTarget, RTB Droid, Яндекс Метрика **плюс** e-commerce, Hybrid,
     ПланФакт (как на `01_схема.jpg`). **ВКонтакте отдельным логотипом НЕ
     показываем.**
   - **Решение: переиспользовать набор логотипов сайта** из
     `assets/images/logos/`, коллаж `02_sources.jpg` не вставлять. Нет
     логотипа в `assets/images/logos/` → взять из `_pptx_extract` и
     оптимизировать, либо текст-чип в стиле сайта (отметить в плане).

5. **Уровни отчётов** — `id="reports"` (новый раздел, расширенный объём)
   - Развёрнуто по слайду 7: Amigo формирует отчёты по ключевым уровням
     рекламной аналитики — кампании, группы и объявления; ключевые слова
     и площадки; география; пол, возраст, устройство; e-commerce и данные
     Яндекс Метрики; средняя позиция клика / объём трафика; лид-формы.

6. **Актуальность данных** — `id="freshness"`
   - Развёрнутый тезис слайда 8 + раскрытие механики со схемы
     `04_refresh_data`: система не разово забирает статистику, а регулярно
     проверяет изменения — ежедневное обновление (каждую ночь свежие
     данные); перезапись изменяемых периодов; проверка прошлых данных
     (сравнение исторических данных за ~180 дней с контрольной базой);
     повторная перезапись при расхождениях.
   - Визуал: схема обновления данных (`04_01_refresh_data.png` — версия
     лучшего качества), оптимизировать.

7. **Мониторинг использования** — `id="monitoring"` (новый раздел; в
   навигатор FR-2a НЕ включён)
   - По слайду 11: система отслеживает, как используются дашборды, сколько
     данных занимает каждый клиент и сколько серверного времени требуется
     на обслуживание проектов. **Тема ролей/пользователей по-прежнему НЕ
     раскрывается** (решение заказчика) — только мониторинг использования
     и ресурсов, без описания ролевой модели.

8. **Финальный CTA** — `id="demo"` (в навигатор FR-2a НЕ включён)
   - Кнопка, открывающая существующий lead-modal в режиме демо-доступа:
     `<button class="… js-lead-open" data-lead-title="Получить демо доступ" …>`
     с теми же data-атрибутами, что и существующая кнопка демо на главной
     (НЕ дублировать сам модал — он один, `#leadModal`).
   - **Решение:** на `product.html` встраивается та же разметка `#leadModal`
     + подключается `js/main.js` целиком (модал работает на месте;
     `initLeadFormModal`, cookie-баннер и чат-виджет — как на главной, для
     единообразия). Один модал, разметка `#leadModal` копируется 1:1.
   - **Тарифы на product.html НЕ нужны** (решение заказчика). Блок тарифов
     и коллаж `06_prices.jpg` не добавляются; при необходимости — текстовая
     ссылка/кнопка «Тарифы» на секцию тарифов `index.html`.

### FR-2a. Разделы навигатора (точный список пунктов FR-1b)
Пункты внутристраничной навигации (слева направо, с переносом на узких
экранах), каждый ведёт на `id` секции из FR-2:

**Навигатор — 6 пунктов (решение заказчика, Q15):**

1. **Проблема** → `#problem`
2. **Что такое Amigo** → `#what`
3. **Поток данных** → `#data-flow`
4. **Источники** → `#sources`
5. **Уровни отчётов** → `#reports`
6. **Актуальность данных** → `#freshness`

- **«Мониторинг» (`#monitoring`) и «Демо-доступ»/CTA (`#demo`) в навигатор
  НЕ включаются** (решение заказчика). Сами секции остаются на странице
  с теми же `id` — просто без пунктов в полосе навигации.
- Hero в навигаторе не присутствует (это верх страницы).
- Тексты пунктов короткие (для компактности полосы); финальные
  формулировки можно слегка скорректировать при вёрстке, но смысл и `id`
  сохраняются.

### FR-3. Точка входа «О нас»
- В `index.html` ссылки «О нас» меняют `href` с `#about` на `./product.html?v=N`:
  - навигация в шапке (строка ~62);
  - футер (строка ~565).
- Те же ссылки «О нас» должны присутствовать и работать в шапке/футере самой
  `product.html` (ведут на `index.html` для возврата по другим пунктам меню).
- **Решение заказчика:** переиспользуем существующий пункт «О нас» (новый
  пункт меню НЕ добавляем; переименование пункта — позже, вне этой задачи).
- **`#about`-секция на главной и пункт футера «Аналитика» (→ `#about`) —
  оставить как есть**, не трогать.

### FR-4. Ассеты-изображения
- Выбранные исходники из `source-materials/new-page/` переносятся в
  `assets/images/` по конвенции проекта (как с логотипами: при необходимости
  оригинал в `*_raw`-расположении, оптимизированная версия рядом).
- Имена файлов — латиница, kebab-case, осмысленные
  (например `product-data-flow.png`, `product-data-refresh.png`).
- Крупные PNG-схемы при возможности ужать (страница не должна тянуть
  мегабайтные изображения без необходимости).
- `source-materials/` и распакованный `_pptx_extract/` не коммитятся —
  добавить `source-materials/` в `.gitignore` (см. Open Questions).

### FR-5. Кеш-бастинг (обязательное правило проекта)
- Любая правка CSS/JS/HTML требует поднятия версии `?v=N` во ВСЕХ местах,
  где она используется: `index.html` (ссылки на css/js/privacy/новый
  product), `privacy.html`, новый `product.html`. Текущее значение — `v=48`,
  **поднять до `v=49`** (решение).
- Ссылка на `product.html` из `index.html` тоже идёт с `?v=N`.

### FR-6. Соответствие конвенциям проекта
- CSS добавляется в `css/style.css` в подходящую секцию, классами, через
  `:root`-переменные; инлайн-стили не плодить.
- **Reduced-motion (Variant B):** не оборачивать декоративную/hover-анимацию
  новой страницы в `@media (prefers-reduced-motion: reduce){…: none}`.
  Подавляется только непрерывный пульс `.status-dot`, если он есть.
- Любой динамически вставляемый текст (если будет) проходит через
  `escapeHtml` — но на этой статической странице JS-инъекций контента не
  предполагается, кроме штатной работы lead-modal/cookie/чат-виджета из
  `main.js`.
- Если на страницу подключается `js/main.js` — все `initX` самодостаточны и
  no-op при отсутствии своих элементов, ничего дополнительно отключать не
  нужно.

### FR-7. Источники контента
- Контент страницы синтезируется из ДВУХ источников:
  1. `source-materials/new-page/amigo_presentation.pptx` (+ извлечённый
     текст в `_slides_text.txt`, визуалы в `_pptx_extract/ppt/media/`);
  2. Google-документ «Product Overview»
     `https://docs.google.com/document/d/1AuKQ5Npw6f7suTQSssODaQR1ryKTZyJH3t3CmCz-FjM`
     (доступ по ссылке; текст экспортируется через `…/export?format=txt`).
- Google-док считается приоритетным по фактам/терминологии (содержит более
  точные формулировки: микросервисы, мастер-БД токенов, слой комиссий/НДС,
  канонический перечень из 6 источников). Маркетинговый тон/структуру брать
  из презентации.
- При противоречиях между источниками — отметить и согласовать с заказчиком,
  не выбирать молча.
- Google-док — внешний и может меняться/закрыться: на момент реализации
  перечитать его заново; не кэшировать факты в коде сверх необходимого.

## Possible Edge Cases
- **Возврат с product.html на главную:** пункты меню с in-page-якорями
  (`#about`, `#pricing` и т. п.) на отдельной странице не сработают как
  плавный скролл — они должны вести на `index.html#anchor`, иначе клики
  «в никуда».
- **Мобильный бургер:** на ≤768px навигация скрыта за бургером; шапка
  product.html должна корректно работать с `initMobileMenu`.
- **lead-modal без JS-инициализации:** если на странице есть `.js-lead-open`,
  но не подключён `main.js`/нет разметки `#leadModal` — кнопка демо ничего не
  откроет. Связка «есть триггер ⇒ есть модал ⇒ подключён main.js» обязательна.
- **Тяжёлые изображения:** исходные PNG до ~3.7 МБ; без оптимизации страница
  будет грузиться долго на мобильном.
- **Кеш у вернувшихся посетителей:** без поднятия `?v=N` ссылка «О нас»
  поведёт на новую страницу, но старый кешированный CSS может её сломать.
- **Дубль пункта меню:** если добавить новый пункт вместо переиспользования
  «О нас», в меню окажутся и якорь, и страница — путаница в навигации.
- **Cookie-баннер/чат-виджет:** при подключении `main.js` на product.html
  снова появятся cookie-баннер и чат — нужно решить, желательно ли это на
  этой странице (вероятно да, для единообразия).
- **Навигатор и якорный скролл:** клик по пункту навигатора прыгает к
  секции; заголовок секции не должен «уезжать» под шапку/навигатор
  (учесть отступ-скролл, особенно если навигатор когда-нибудь сделают
  sticky). Поведение скролла не отключать под reduced-motion (Variant B).
- **Рассинхрон навигатора и секций:** если переименовать/удалить секцию,
  но забыть пункт FR-2a (или наоборот) — «битый» якорь. Список FR-2a и
  `id` секций FR-2 правятся синхронно.
- **Навигатор vs. бургер шапки:** на ≤768px и навигатор, и бургер-меню
  присутствуют — не должны конфликтовать визуально/по кликам.

## Acceptance Criteria
- [ ] `product.html` существует, открывается локально и визуально
      неотличим по стилю от остального сайта: шрифты, цвета, типографика,
      отступы, кнопки, шапка и подвал — из общего `css/style.css`, через
      переиспользование существующих классов/переменных (FR-1a).
- [ ] Страница содержит расширенные секции с `id`: hero (без id), проблема
      `#problem`, что такое Amigo `#what`, поток данных `#data-flow`,
      источники `#sources`, уровни отчётов `#reports`, актуальность данных
      `#freshness`, мониторинг `#monitoring`, финальный CTA `#demo`. Тема
      ролей/пользователей НЕ раскрывается.
- [ ] Под шапкой, в `<body>`, есть статичный внутристраничный навигатор
      (FR-1b/2a): **6 текстовых ссылок-якорей** (Проблема, Что такое Amigo,
      Поток данных, Источники, Уровни отчётов, Актуальность данных),
      активный подчёркнут со scroll-spy, переносятся на узких экранах,
      по клику — плавный скролл, стиль из общего CSS (как в
